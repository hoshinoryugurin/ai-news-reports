### 1. AIエージェントは「動く」から「評価しながら動く」へ

GitHub Copilotのagentic harness評価、GUIエージェントの経験学習、Claude Tagのような共有場所に常駐するAIなど、AIが作業空間で継続的に動く前提が強まった。一方で、モデル別・タスク別の評価、実行ログ、失敗後の学習がセットで必要になっている。

### 2. AI運用は、秘密・コスト・停止条件を含むシステム設計になった

GitHubの資格情報失効、HF Jobsでの一時的な推論サーバー起動、低コスト・省電力モデルの流れから、AIは「常に強いモデルを使う」ではなく、必要な時だけ動かし、危ない時は止める部品として扱う方向が見えた。

### 3. 予測AI・world modelは「それっぽさ」だけでは危ない

リアルタイム音声AIが声のニュアンスを十分に聴けない問題、world modelの幻覚検知、Model Forensicsなど、AIの出力が自然に見えても、根拠・原因・現実とのズレを確認する必要があるというテーマが続いた。

### 4. 個別文脈を持つAI支援が増えている

データ分析エージェント、生活や健康のDigital Twin、共有場所に常駐するAIなど、単発回答ではなく、長期ログや個別状況をもとに支援する方向が強くなっている。

ユグ的に気になるもの特集: 「見張れるAI」を前提にしたReptile Environment OS

今週いちばん気になるのは、AIを賢くする話よりも AIを見張れる形で運用する話 なのだ。

Reptile Environment OSでAIを使うなら、最初から以下をセットにしたい。

  • タスク別モデル選択: 日報要約は軽量モデル、異常時の原因推定は高性能モデル、コード修正は開発向けモデル、というように役割を分ける。
  • 根拠ログ: 「温度が低いかも」と言うだけでなく、参照したセンサー、時刻、過去平均との差、推論の理由を残す。
  • 停止条件: 空調・照明・通知など現実に影響する操作は、閾値、手動確認、タイムアウト、ロールバックを持つ。
  • 失敗の切り分け: AIが変な提案をした時、モデルの問題、センサー欠損、ルール不足、プロンプト、権限設定を分けて調べる。

小さな実験としては、まず「日次ケージ環境レポート」に根拠行を付けるのがよさそう。たとえば、温度・湿度・照明・前日平均との差をAIに渡し、出力に 参照データ と 注意度 と 手動確認が必要な理由 を必ず含める。これなら制御に入る前に、安全な評価ログの型を育てられる。
